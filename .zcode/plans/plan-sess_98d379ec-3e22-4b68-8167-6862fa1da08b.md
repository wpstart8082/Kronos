# Kronos 预测服务 API 化 + 管理后台 + Docker 部署方案

## Context（背景与目标）

本仓库是 Kronos K 线预测模型的 fork，推理核心在本地包 `model/`（`KronosPredictor.predict/predict_batch`，接口稳定、无需修改）。现有 `webui/` 是 Flask debug 原型：全局单例模型、无鉴权、无并发控制、无配置/日志/部署设施，不能直接对外提供服务。

目标：新建独立的生产级服务 `kronos_service/`，将预测能力封装为 REST API（客户端自带 K 线数据），配套管理后台（配置/密钥/监控/自检），Docker GPU 部署（宿主机 4090 直通），模型权重挂载宿主机项目目录。已确认：FastAPI、仅客户端数据、仅 GPU、同步+异步双模式、管理后台 Vue3 + Element Plus + ECharts（CDN 引入，零构建）。现有 `webui/` 与 `model/` 保持不动。

## 一、总体架构

单容器单进程 FastAPI 服务（uvicorn，1 worker——模型常驻进程内存，GPU 单卡下多 worker 只会复制显存，水平扩展靠多容器）：

```
调用方 ──X-API-Key──> FastAPI (端口 8000)
   ├─ /v1/*         预测 API（鉴权 + 限流 + 配额 + 计数）
   ├─ /api/admin/*  管理后台 API（JWT，账密来自 .env；登录失败限速防爆破）
   ├─ /admin        管理后台 SPA（Vue3 + Element Plus + ECharts，CDN 静态页）
   └─ /healthz /readyz  探活（无鉴权，供 Docker healthcheck）

推理管线：请求 → 参数校验(Pydantic) → 入有界队列 → worker 线程(GPU信号量限并发)
          → KronosPredictor.predict(verbose=False) → 响应/写任务表 → 请求日志经内存缓冲由后台写线程批量落库
模型加载：优先读挂载目录 /models/<name>/(config.json+model.safetensors)
          → 未找到则 HF Hub 下载（HF_HOME 指向挂载卷，权重落在宿主机）
          → 模型齐全时可设 HF_HUB_OFFLINE=1 完全离线启动
存储：SQLite(WAL) —— api_keys / request_logs / tasks / runtime_config 四表
停机：SIGTERM → 拒绝新请求 → 队列任务跑完或超时后退出
```

**Docker 用宿主机 GPU 的可行性（已核实）**：Windows + Docker Desktop（WSL2 后端）下，装好较新 NVIDIA 驱动（≥531）即可，WSL2 自动直通 GPU，无需在宿主机装 CUDA Toolkit。compose 用 `gpus: all`（等价长写法 `deploy.resources.reservations.devices: [driver: nvidia, count: all, capabilities: [gpu]]`，两者均支持）。

## 三、API 设计

鉴权：业务接口要求 `X-API-Key: kron-<32位>`；密钥由管理后台签发（仅创建时一次性展示明文），库存 SHA-256 哈希，支持启用/禁用、过期时间、每分钟限速、每日配额、备注。

| 接口 | 说明 |
|---|---|
| `GET /v1/models` | 可用模型列表 + 当前已加载状态（mini/small/base，ctx 长度） |
| `POST /v1/predict` | 同步预测。请求体 `{model?, symbol?, data:[{timestamp,open,high,low,close,volume?,amount?}], lookback?, pred_len, temperature?, top_k?, top_p?, sample_count?, future_timestamps?}`（symbol 仅用于日志标识与按标的统计）；响应含 `timings{queue_ms,inference_ms,total_ms}` 与逐根预测 K 线；超过同步超时（默认 120s，可配）返回 408 + task_id，结果仍可经任务接口获取 |
| `POST /v1/predict/async` | 同请求体，立即返回 `202 {task_id, status_url}` |
| `GET /v1/tasks/{task_id}` | 任务状态 `queued/running/succeeded/failed` + 结果（仅任务所属密钥可查） |
| `GET /healthz` `/readyz` | 存活 / 就绪（模型已加载且队列可用），无鉴权 |
| `/api/admin/*` | login、overview(监控总览)、keys CRUD、config 读写、models load/unload、logs 查询（含按密钥/标的/错误的明细）、selftest 触发 |

安全边界（Pydantic 强校验 + 请求体大小中间件）：pred_len≤480、lookback≤模型 ctx、sample_count≤8、data 行数上限、temperature/top_p 合法区间。

## 四、管理后台功能（对应原始 4 点要求）

1. **登录**：账密来自 `.env`（`KRONOS_ADMIN_USERNAME/PASSWORD`，常数时间比较），JWT 会话，登录接口限速防爆破。
2. **监控仪表盘**（ECharts + el-card/el-statistic）：服务状态（版本/运行时长/队列深度/排队与推理耗时 p50/p95/失败任务数）；请求统计（1h/24h 调用量、成功率、错误分布、按密钥与按 symbol 用量 Top N）；系统资源（CPU/内存 psutil；GPU 型号/显存 torch.cuda）。
3. **接口配置**（el-table + el-dialog 表单）：API 密钥管理（签发/吊销/启停/限速/配额/用量查看、单密钥调用明细与错误信息，便于排查接入方问题）。
4. **系统配置**（el-form，存 DB、后台热生效，`.env` 只放密钥与路径）：默认模型、预加载模型、推理并发数、同步超时、合批开关、各参数上限、日志保留天数。
5. **服务自检**：一键并发跑自检项并逐项展示通过/失败+耗时——模型冒烟预测（tests/data/regression_input.csv，小 pred_len，校验输出无 NaN/形状正确）、GPU 检测、SQLite 读写、模型挂载目录扫描。

## 五、Docker 部署（GPU + 模型挂载宿主机）

`docker-compose.yml` 要点：
```yaml
services:
  kronos-api:
    build: .
    gpus: all                      # 4090 直通；等价写法 deploy.resources.reservations.devices
    env_file: .env
    ports: ["8000:8000"]
    volumes:
      - ./models:/models           # 模型挂载宿主机项目目录（含 hf_cache/）
      - ./volumes/instance:/app/instance   # SQLite
      - ./volumes/logs:/app/logs           # 运行日志
    healthcheck:                    # pytorch 镜像不带 curl，用 python 探活
      test: ["CMD", "python", "-c", "import urllib.request;urllib.request.urlopen('http://localhost:8000/healthz')"]
      interval: 30s
      timeout: 5s
      retries: 3
    stop_grace_period: 120s        # 等待在跑推理收尾
    restart: unless-stopped
```
- 宿主机 `./models/` 结构：`Kronos-base/`、`Kronos-small/`、`Kronos-mini/`、`Kronos-Tokenizer-base/`、`Kronos-Tokenizer-2k/`（各含 config.json + model.safetensors）。`scripts/download_models.py` 一键完成（优先从本机已有 HF 缓存 `C:\Users\wpmai\.cache\huggingface\hub` 拷贝 Kronos-base 与 Tokenizer-base，缺失的联网下载）。
- Dockerfile：`pytorch/pytorch:2.6.0-cuda12.4-cudnn9-runtime` 基镜像（自带 torch CUDA 版，4090/sm_89 支持）+ pip 装服务依赖 + 非 root 用户；镜像压缩体积约 3.1GB。
- 离线与首启说明：模型齐全时 `.env` 设 `HF_HUB_OFFLINE=1` 秒级启动；`./models` 为空时首启会从 HF 下载（base 约 400MB），需联网且耗时数分钟——README 说明。
- 宿主机要求：仅 NVIDIA 驱动 + Docker Desktop（WSL2 后端），无需装 CUDA；容器 TZ 可配以对齐调用方时区。

## 七、验证方式

1. **本地**：`scripts/download_models.py` 准备 `./models/` → `uvicorn kronos_service.app.main:app` 启动 → curl 验证：无密钥 401、持密钥同步预测 200（含耗时分解）、异步提交+轮询、限流触发 429、`/readyz` 就绪、畸形数据 422。
2. **管理后台**：浏览器完成登录（错密 5 次触发限速）→ 签发密钥（明文仅展示一次）→ 改配置热生效 → 跑自检（显示 4090 型号、冒烟预测通过）→ 仪表盘 ECharts 看到调用量趋势/延迟分布/按 symbol 统计。
3. **Docker**：`docker compose up -d --build` → healthcheck 变 healthy → 自检页确认容器内 GPU 可用 → 删除宿主机某模型目录后管理页正确显示缺失 → 重启容器 SQLite/日志仍持久化 → `docker compose down` 期间在跑任务优雅收尾。
4. **并发**：脚本并发打 20 个请求，观察队列排队指标与 p95 延迟，验证无 5xx、无 OOM。
